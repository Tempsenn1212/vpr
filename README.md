# Telegram Mini App «Учёт документации ВПР»

Работающий клиент React/TypeScript, сервер Node.js 24/Express, постоянная SQLite-база, миграция, синтетические пользователи и автоматические проверки. Файлы документов не хранятся. Исходное ТЗ: `docs/VPR_Codex_TZ.md`.

## Быстрый запуск с синтетическими данными

Требуется **Node.js 24.x**, npm. Из корня распакованного проекта:

```sh
npm ci
npm run dev
```

Открыть **http://localhost:5173**. `npm run dev` явно включает серверный тестовый вход, поднимает API на 3000 и Vite на 5173. Создаются четыре работника и один начальник. Работник Анна Смирнова — синтетический администратор, начальник Елена Соколова — отдельная рабочая роль. Все аккаунты и Telegram ID вымышлены. Войти другим участником можно в отдельном браузерном профиле либо после выхода кнопкой вверху. База: `data/vpr.sqlite`; перезапуск её не очищает.

Если создаёте `.env` из `.env.example`, для разработки оставьте `APP_ORIGIN=http://localhost:5173`. Используйте именно этот адрес: сервер проверяет Origin изменяющих запросов. Для другого адреса задайте его явно.

Для запуска собранного приложения без Vite:

```sh
npm run build
NODE_ENV=development DEV_AUTH=true APP_ORIGIN=http://localhost:3000 npm start
```

Открыть http://localhost:3000. На Windows PowerShell задайте эти переменные через `$env:ИМЯ='значение'` перед `npm start`.

## Проверки

```sh
npm test
npm run build
npm run test:e2e
```

`npm test` запускает доменные и HTTP-интеграционные тесты на временных БД. `test:e2e` сначала собирает клиент, затем поднимает изолированный сервер на 4173 и запускает Playwright. Нужен Chromium: по умолчанию `/usr/bin/chromium`; другой путь передать через `CHROMIUM_PATH`. Можно выполнить `npx playwright install chromium`, затем указать путь установленного Chromium в `CHROMIUM_PATH`. Параллельные пользовательские контексты имеют независимые cookies. HTML-отчёт: `playwright-report/index.html`. Результаты проверки критериев — `docs/ACCEPTANCE.md`.

## Подключение к Telegram и production

Реальные аккаунты и токен для локальной разработки не нужны. Подключение выполняется после получения реквизитов.

1. Создать бота через BotFather. Получить токен и Telegram ID первоначального администратора вне приложения.
2. Собрать проект (`npm ci && npm run build`). На сервере безопасно настроить переменные окружения: `NODE_ENV=production`, `DEV_AUTH=false`, `BOT_TOKEN`, `INITIAL_ADMIN_TELEGRAM_ID`, `APP_ORIGIN=https://ваш-домен`, `DATABASE_PATH=data/production.sqlite`, `APP_TIMEZONE=Europe/Moscow`.
3. Использовать **новую, чистую production-БД**. Сервер откажется запускаться в production с синтетической БД или включённым DEV_AUTH. Для первого запуска обязателен явно заданный положительный Telegram ID администратора. Первый посетитель никогда не получает права автоматически.
4. Запустить `npm start` за HTTPS reverse proxy. `docs/Caddyfile.example` содержит пример Caddy. Приложение должно обслуживаться в корне домена; API и клиент имеют один Origin. Прокси должен передавать Cookie/Set-Cookie без изменений, не кешировать `/api` и не добавлять CORS с посторонними источниками.
5. В BotFather настроить кнопку меню бота / Mini App на HTTPS URL, например `/setmenubutton`. Для Main Mini App использовать настройки бота. Открыть приложение из Telegram, войти администратором и добавить допущенные Telegram ID через «Управление».
6. Проверить на настоящих Telegram iOS/Android/Desktop: вход, светлую/тёмную тему, cookies, повторное открытие после истечения сессии и отзыв доступа.

Токен хранится только на сервере; `.env` исключён из Git, Docker-контекста и архива. Telegram SDK передаёт **сырой `Telegram.WebApp.initData`** серверу. `initDataUnsafe` не используется. HMAC-SHA-256 и `auth_date` проверяются по [официальной документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), сверенной при реализации 11.11.2026. Подписываются все поля кроме `hash`, включая `signature`, если оно присутствует. Повторяющиеся ключи запрещены; максимальная давность — 300 секунд, допустимое опережение часов — 30 секунд. Часы сервера должны быть синхронизированы.

После проверки создаётся непрозрачная серверная сессия на 8 часов; в БД хранится хеш токена. Cookie — HttpOnly, SameSite=Strict, Secure в production. Для Telegram Web, открывающего Mini App в стороннем iframe, ограничения браузера на сторонние cookies могут потребовать отдельной адаптации механизма сессии; этот сценарий должен быть проверен на реальных клиентах перед вводом в эксплуатацию. В нативном Telegram Mini App работает в своём WebView.

Каждый API-запрос повторно читает активность и роль участника из БД. Переданная клиентом роль не используется. Администратор изначально имеет роль работника и **не** получает права подтверждения. Через управление можно назначить ему рабочую роль начальника отдельно.

Bootstrap сохраняется однократно в `meta.initialized`. Передача администратора — транзакция в БД: сначала выдаётся право выбранному активному участнику, затем снимается у передающего. Перезапуск и прежний `INITIAL_ADMIN_TELEGRAM_ID` не отменяют передачу. Отключить текущего администратора нельзя: сначала передать управление. Отключённые участники и их история остаются в БД.

## Docker Compose

```sh
docker compose --profile demo up --build -d demo
```

Демо: http://localhost:3000, отдельный именованный volume `demo-data`.

Production: установить серверные переменные через защищённый `.env` / менеджер секретов, создать доступный для UID 1000 каталог `backups`, затем:

```sh
docker compose --profile production up --build -d app
```

Снаружи контейнера порт привязан к 127.0.0.1:3000 для HTTPS-прокси. SQLite и WAL размещены в постоянном `production-data`. Контейнер работает от непривилегированного пользователя. Не запускайте demo и app одновременно на одном порту. В сетях с инспекцией TLS Dockerfile поддерживает необязательный BuildKit secret `proxy_ca`; обычному хостингу он не требуется.

Один экземпляр Node обслуживает приложение. SQLite/WAL подходит для общей работы небольшой группы; отдельный процесс СУБД не требуется. Не размещайте БД на NFS и не поднимайте несколько реплик сервера с независимыми файлами БД. При значительном росте нагрузки переносить модель на PostgreSQL.

## Переменные окружения

| Переменная                  | Значение                                                        |
| --------------------------- | --------------------------------------------------------------- |
| `NODE_ENV`                  | `production` включает строгие проверки запуска и Secure cookies |
| `DEV_AUTH`                  | Только явное `true` разрешает синтетический вход вне production |
| `PORT`                      | 3000 по умолчанию                                               |
| `APP_ORIGIN`                | Полный Origin клиентского приложения без завершающего `/`       |
| `APP_TIMEZONE`              | Europe/Moscow по умолчанию; валидируется при старте             |
| `DATABASE_PATH`             | `data/vpr.sqlite` по умолчанию                                  |
| `BOT_TOKEN`                 | Секрет токена бота, только сервер                               |
| `INITIAL_ADMIN_TELEGRAM_ID` | Обязателен на первой инициализации реальной БД                  |

Зависимости закреплены в `package-lock.json`; устанавливать через `npm ci`. SQLite встроен в Node 24. Миграции из `server/migrations` применяются при старте по `PRAGMA user_version`. В текущей версии одна начальная миграция. Для будущих изменений добавлять последовательные миграции, не менять применённую схему задним числом.

## Бизнес-правила и принятые решения

- Название: 1–200 символов после trim, причина: 1–1000, имя/категория: 1–100. Даты строго `YYYY-MM-DD` в пределах 1900–2200. Срок может быть прошлым; фактическое вложение не может быть будущим и может предшествовать созданию карточки.
- Дата срока/вложения — календарные строки ISO в SQLite, времена событий — UTC ISO. Расчёт календарных дней не зависит от часового пояса ОС; «сегодня» берётся из IANA `APP_TIMEZONE`. Позднее подтверждение не меняет своевременность вложения.
- Разрешены только действия, а не произвольная запись статуса. Прямое вложение не создаёт оформления. Отклонение убирает действующее вложение, оставляя его в аудите. Возврат в работу очищает отметки, отзыв подтверждения возвращает PLACED.
- Изменение названия, категории, срока или фактической даты подтверждённой карточки требует явного подтверждения сброса и возвращает PLACED. Сохранение без фактической разницы не меняет ни подтверждение, ни версию.
- Логическое удаление сохраняет карточку, события и снимки. Скрыть категорию можно после обработки или переноса всех незавершённых карточек. Каскадного удаления категорий нет; переименование/порядок/скрытие фиксируются в аудите.
- Копирование открывает новую форму с названием и категорией; срок пустой. Сервер создания всегда назначает новый ID, текущего автора и IN_PROGRESS, игнорируя переданные чужие отметки.
- Массовое подтверждение получает **явный список ID и версий**, период и категорию (`ALL` — явный режим). Сервер повторно проверяет всё в транзакции. Результат содержит точные подтверждено/пропущено/конфликт, каждое успешное событие — общий batch ID. Незавершённые прошлых периодов показаны отдельно и автоматически не добавляются.
- Проверка периода не меняет статусы. Каждый раз сохраняются границы, полные карточки с версиями и итогами. Снимки доступны даже после смены расписания или удаления карточек.
- Обновление клиентов — опрос каждые 2 секунды, без перекрывающихся запросов. При ошибке связи остаются последние данные с предупреждением. После восстановления выполняется актуальный запрос. Открытый черновик не перезаписывается опросом.
- Все изменяющие бизнес-запросы требуют `Idempotency-Key`. Результат и отпечаток запроса сохраняются в той же транзакции. Клиент при неопределённом сетевом исходе повторяет тот же запрос с тем же ключом. Иное тело с прежним ключом отклоняется. Конфликт версии — HTTP 409 со свежей карточкой; черновик можно сохранить для сверки и явно загрузить актуальные поля.
- Сессии отзываются сразу при отключении. Смена роли действует на следующем запросе. Аудит хранит ID и имя автора на момент события; содержит полные старые/новые данные и имена категорий на момент действия. API редактирования/уничтожения аудита отсутствует.

### Правило перехода расписания (из раздела 11 ТЗ)

Начальный отсчёт — 13.11.2026, интервал — 14 календарных дней. 13 ноября проверки нет. Первый период **14–27 ноября**, второй **28 ноября – 11 декабря**. Выбор документов идёт по сроку с обеими границами включительно.

После начала первого периода новая версия действует **со дня после конца текущего периода**. Первый новый период завершается в первую дату `новый отсчёт + k × интервал`, `k >= 1`, которая строго позже конца старого периода (то есть не раньше первого дня нового). Этот переходный период может иметь другую длину; интерфейс показывает его в предварительном расчёте. Затем следуют полные интервалы. Повторное изменение до вступления новой версии заменяет её на той же границе, сохраняя все версии и аудит. До начала первого периода разрешена полная замена исходных настроек. Старые снимки проверок неизменны. Новые интервалы не привязываются к пятнице. Интервал — целое число 1–3660 дней.

Пример: смена 20.11 с исходного расписания на отсчёт 10.11 и 10 дней сохраняет 14–27.11, создаёт переходный 28–30.11, затем 01–10.12 и 11–20.12.

## Резервное копирование и восстановление

Онлайн-копия использует SQLite backup API, согласованно включает WAL и проверяется `PRAGMA integrity_check`:

```sh
npm run backup -- backups/vpr-backup.sqlite
```

Для другой БД задать `DATABASE_PATH`. Для контейнера (каталог backups должен быть доступен UID 1000):

```sh
docker compose --profile production exec app node scripts/backup.mjs /app/backups/vpr-backup.sqlite
```

Сохранять копии вне сервера с ограниченным доступом, регулярно проверять восстановление. Не копировать только основной файл работающей SQLite при активном WAL.

Восстановление без Docker:

1. Остановить сервер, чтобы никто не писал в БД.
2. Сохранить текущие `vpr.sqlite`, `vpr.sqlite-wal`, `vpr.sqlite-shm` в отдельную папку для отката (если файлы существуют).
3. Убедиться в целостности копии (`PRAGMA integrity_check` на ней), перенести файл копии на `DATABASE_PATH`. Старые WAL/SHM не должны оставаться рядом с восстановленным основным файлом: переместить их в папку отката.
4. Проверить права владельца и запустить сервер. Сверить карточки, историю, администратора и снимки.

Для Docker сначала `docker compose --profile production stop app`, затем с помощью одноразового контейнера с подключённым `production-data` выполнить те же операции в `/app/data` и перезапустить app. Именованный volume не удалять. Восстановленная база содержит сессии и права на момент копии; при необходимости отозвать сессии контролируемой SQL-командой `DELETE FROM sessions` на остановленном сервере.

## Структура

- `client/` — React, типы, API с повтором ключей запросов, адаптивные темы.
- `server/domain.mjs` — чистые правила дат, переходов и периодов.
- `server/store.mjs` — транзакционные операции и снимки.
- `server/auth.mjs` — Telegram HMAC и серверные сессии.
- `server/app.mjs` — API, доступ, проверка Origin, лимит попыток входа, выдача клиента.
- `server/migrations/001_initial.sql` — схема; `seed.mjs` — только синтетические данные.
- `tests/` — доменные, HTTP и браузерные тесты.
- `scripts/` — запуск разработки, временный E2E-сервер, резервное копирование.

## Границы проверки

Проект проверяется локально с синтетическими данными и подписанными тестовыми Telegram payload. Реальный запуск внутри Telegram, настоящий бот, домен, TLS и политика cookies Telegram Web требуют реквизитов и отдельной проверки. Приложение не публиковалось как общедоступный сервис. Оповещений бота, загрузки файлов, экспорта и внешних интеграций нет.

Для небольшой группы ответ состояния включает все карточки и аудит; это упрощает согласованное восстановление клиента после разрыва. При накоплении большого аудита понадобятся пагинация и инкрементальные обновления. SQLite-операции синхронны и выполняются в одном серверном процессе; нагрузочные испытания не проводились.
