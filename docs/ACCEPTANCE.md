## Изменение требований пользователя от 15.11.2026

Проверка и подтверждение начальником необязательны для всех категорий. Основной цикл: «В работе» → при необходимости «Оформлен» → «Вложен в журнал» (завершён). Дополнительное подтверждение, отклонение и снимки проверок доступны начальнику; права на эти действия сохранены. Это обновление применяется к исходной матрице ТЗ ниже.

- После вложения работником API возвращает `completed: true`, хотя подтверждения и записи проверки нет. События содержат только реальные действия участников.
- PLACED и CONFIRMED входят в завершённые, не попадают в список незавершённых прошлых периодов и позволяют скрыть категорию, если других незавершённых карточек в ней нет.
- Отзыв или сброс дополнительного подтверждения сохраняет завершённость. Отклонение вложения и возврат в работу снова делают документ незавершённым.
- Убраны счётчик ожидающих обязательного подтверждения и предупреждения о непроведённых плановых проверках. На главной показано число завершённых, в карточке объяснена необязательность проверки.
- Существующие PLACED после повторного открытия БД считаются завершёнными без переписывания карточек и аудита. Старые снимки сохранены; новые содержат количества завершённых и незавершённых.
- Добавлены три серверных регрессионных сценария и браузерный сценарий завершения работником без проверки с проверкой главной страницы и незавершённых прошлых периодов.
- Проверка обновления: `npm test` — **37/37**, TypeScript/Vite — успешно, Playwright — **11/11**.

## Десять браузерных сценариев

1. Два клиента: создание → появление без reload → оформление другим участником → правильное имя исполнителя; у работника нет кнопки подтверждения.
2. Мобильный экран: ошибки обязательных полей, длинное название, вложение, копия с пустым сроком, тёмная тема, удаление и просмотр истории удалённой карточки.
3. Начальник: выбор категории/всех PLACED, исключение карточки, фиксация проверки и событие в истории.
4. Обрыв API-запросов: форма и ошибка вместо успеха, восстановление связи и сохранение.
5. 360 px: пустой поиск, светлая тема, отсутствие горизонтального переполнения.
6. Две формы: чужая сохранённая правка не перезаписывается; черновик остаётся; явная загрузка текущей версии.
7. Управление: добавление участника и категории, расчёт расписания; администратор с ролью работника не получает подтверждение.

8. Telegram Web без cookies: проверка подписанного синтетического initData, создание карточки, повторное открытие страницы. Сессия передаётся в Authorization; localStorage/sessionStorage остаются пустыми.
9. Отказ Telegram-входа не заменяется ошибками фонового опроса; до авторизации запросы состояния не выполняются.
10. Недоступный Telegram SDK даёт конкретное сообщение вместо неопределённого отказа сессии.

## Исправление входа в Telegram Web

Воспроизведено поведение, совпадающее с сообщением пользователя: Telegram-вход прошёл, но без cookie последующий запрос состояния возвращал 401. Оба новых регрессионных теста (сессия без cookies и сохранение причины отказа) падали на прежней версии. Исправление добавляет передачу того же непрозрачного серверного токена в Authorization и сохраняет его только в памяти страницы. Cookie-вход совместим с прежним механизмом; схема БД не менялась. Проверка подписи, срок сессии, роли и отзыв доступа продолжают проверяться сервером. Дополнительные HTTP-тесты проверяют вход в production без cookies, права, отключение, истечение, logout и отклонение поддельных токенов.
