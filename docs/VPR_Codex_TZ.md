# Техническое задание для Codex
# Telegram Mini App «Учёт документации ВПР»

Версия 1.0 · 11 ноября 2026 года

## 1. Задача для Codex

Разработать работоспособное Telegram Mini App для общего учёта карточек документов, сроков их предоставления и подтверждения выполнения начальниками. Реализовать интерфейс, сервер, постоянную базу данных, авторизацию, разграничение прав, обновление данных между пользователями и проверки бизнес-логики. Результат — запускаемый проект с инструкцией, а не только макет.

Это самостоятельное задание: не требуется доступ к исходной переписке. Сначала изучить существующий репозиторий, если он предоставлен, и сохранить совместимые решения. При отсутствии проекта создать новый. Не добавлять функции за пределами первой версии без необходимости.

Продуктовые требования ниже согласованы. Раздел 11 содержит предлагаемые технические решения и правила для неоднозначных случаев: использовать их как исходные значения, явно описать в README. Конкретный стек не является жёстким требованием.

## 2. Назначение и границы первой версии

Работники выполняют общую работу. Документ доводят вне приложения, собирают подписи, затем физически вкладывают в журнал, находящийся в канцелярии. В приложении отражают этапы и сроки. Начальник наблюдает за изменениями и подтверждает вложение.

- Хранить только карточки. Файлы, фотографии, сканы, содержимое документов и электронные подписи не загружать.
- Все допущенные пользователи видят все документы. Подразделений, личных списков доступа и обязательного ответственного нет.
- Начальные пользователи: четыре работника; число начальников будет уточнено. Не ограничивать количество программно.
- Разрешить выполнение и отметку вложения любым участником независимо от автора карточки.
- Уведомления, рассылки бота, автоматическая генерация еженедельных документов, экспорт и интеграции с внешними системами не входят в первую версию.
- Язык интерфейса — русский. Основное использование — Telegram на телефоне; интерфейс также пригоден для Telegram Desktop.

## 3. Участники и права

Рабочие роли: «Работник», «Начальник». Администратор — отдельное право управления, совместимое с любой рабочей ролью; оно само по себе не даёт права подтверждать документы.

| Действие | Работник | Начальник |
|---|---|---|
| Читать все карточки и историю | Да | Да |
| Создавать, изменять, копировать и удалять любые карточки | Да | Да |
| Отмечать оформление и вложение в журнал | Да | Да |
| Указывать фактическую дату вложения раньше дня нажатия | Да | Да |
| Подтверждать вложение, отклонять отметку с причиной | Нет | Да |
| Массово подтверждать вложение | Нет | Да |
| Фиксировать проведение проверки периода | Нет | Да |

Начальник может подтверждать собственное вложение; проверка другим начальником не требуется. Везде отображать, кто поставил отметку.

Администратор добавляет и отключает участников, назначает рабочие роли, управляет категориями и передаёт право администратора другому участнику. Изначально администратор — Telegram-аккаунт заказчика. Не угадывать его ID и не назначать администратором первого посетителя. Обеспечить безопасную начальную настройку по указанному Telegram ID и передачу управления без изменения кода. При передаче нельзя оставить приложение без администратора. Отключение пользователя не удаляет его историю.

Расписание проверок могут менять начальники; администратор также может управлять этой настройкой. Изменения фиксируются в истории.

## 4. Категории и карточки

Главный экран — сетка кликабельных иконок категорий. Временно использовать «Иконка №1», «Иконка №2», «Иконка №3». Число, названия и порядок настраиваются; не зашивать фиксированное число категорий в интерфейс.

На плитке отображать название и счётчики активных документов: всего, просрочено без вложения, ожидает подтверждения. Один документ может участвовать в нескольких подходящих счётчиках; явно подписывать их.

Внутри категории — список соответствующих карточек и кнопка «Создать документ». Обязательные поля создания: название, срок предоставления документа. Категория подставляется из текущего раздела. Ответственного заранее не назначать.

В карточке хранить и показывать:

- уникальный идентификатор, название, категорию;
- срок предоставления как календарную дату, без отдельного срока действия;
- текущий статус;
- автора и время создания, время последнего изменения;
- кто и когда отметил оформление;
- кто и когда отметил вложение, фактическую дату вложения;
- кто и когда подтвердил вложение либо отклонил отметку, причину отклонения;
- историю действий и изменений значимых полей.

Название не может быть пустым после удаления крайних пробелов. Срок обязателен. Разрешить прошлую дату срока для учёта существующих документов. Одинаковые названия допустимы. Длину названия разумно ограничить на клиенте и сервере одинаково.

## 5. Статусы и действия

| Код | Точное название для пользователя | Значение |
|---|---|---|
| IN_PROGRESS | В работе | Документ доводят и собирают подписи |
| READY | Оформлен, ожидает вложения в журнал | Все подписи собраны, осталось вложить документ |
| PLACED | Вложен в журнал, ожидает подтверждения | Участник отметил физическое вложение |
| CONFIRMED | Вложение подтверждено | Начальник подтвердил вложение |
| NEEDS_CORRECTION | Требует исправления | Начальник отклонил отметку и указал причину |

Основные переходы:

1. Создание → IN_PROGRESS.
2. «Документ оформлен» → READY. Сохранить автора и время.
3. «Вложен в журнал» из IN_PROGRESS или READY → PLACED. Промежуточное оформление не обязательно. Если его пропустили, не выдумывать отдельную отметку оформления.
4. «Подтвердить вложение» из PLACED → CONFIRMED, только начальник.
5. «Отклонить отметку» из PLACED → NEEDS_CORRECTION, только начальник, причина обязательна.
6. После исправления из NEEDS_CORRECTION разрешить повторное оформление или вложение. Отклонённые сведения остаются в истории и не считаются действующим подтверждением вложения.
7. Начальнику доступно «Вложен в журнал и подтверждён»: из IN_PROGRESS, READY или NEEDS_CORRECTION одним действием зафиксировать вложение и подтверждение от его имени.

Не предоставлять свободный выбор произвольного статуса, позволяющий обойти права. Выполнять переходы через разрешённые действия.

Для исправления ошибочных отметок дать обеим рабочим ролям действие «Вернуть в работу» с подтверждением и причиной. Оно очищает действующие отметки оформления, вложения и подтверждения, сохраняя их в истории. Начальник может отозвать подтверждение с причиной, вернув карточку в PLACED. Все такие действия должны быть заметны в истории.

При изменении названия, категории, срока или фактической даты вложения подтверждённой карточки снять действующее подтверждение и вернуть PLACED, сохранив вложение. Перед сохранением предупредить об этом. Изменение без фактической разницы не сбрасывает подтверждение. Если вложение отменено, вернуть IN_PROGRESS. Старое подтверждение не удалять из истории.

## 6. Срок и фактическая дата вложения

Срок предоставления — последний календарный день, когда документ должен быть вложен в журнал. Оформление само по себе срок не закрывает. День заканчивается в 23:59:59 в часовом поясе приложения.

При отметке вложения предложить сегодняшнюю дату и возможность выбрать более раннюю. Будущую фактическую дату запрещать. Сохранять отдельно фактическую дату и серверное время действия: пользователь может отметить сегодня вложение, выполненное вчера. Разрешить фактическую дату раньше даты создания карточки для ввода существующих документов. Дату не считать независимо проверенным фактом до подтверждения начальника.

Срок отображать отдельно от основного статуса:

- без действующей отметки вложения: «Осталось N дней», «Срок сегодня», «Просрочено на N дней»;
- с действующей отметкой: «Вложен в срок» либо «Вложен с опозданием на N дней»;
- у PLACED сохранять явное указание «Ожидает подтверждения»;
- позднее подтверждение начальника не меняет своевременность фактического вложения;
- после отклонения отметки прежняя дата вложения остаётся в истории, но не закрывает просрочку.

Пример: срок 20 ноября, вложение 20 ноября, отметка в приложении 21 ноября, подтверждение 27 ноября — вложено вовремя, при этом все реальные времена действий видны.

## 7. Проверки периодов и массовое подтверждение

Начальная дата отсчёта: 13.11.2026. Интервал: 14 календарных дней. 13 ноября проверка НЕ проводится. Первая проверка — 27.11.2026, вторая — 11.12.2026.

Первый период: 14–27 ноября включительно; второй: 28 ноября – 11 декабря включительно. Дата проверки — последний день периода. При текущем интервале это каждая вторая пятница. Не подменять период скользящими «последними 14 днями».

В период включать все неудалённые документы, срок предоставления которых попадает в его границы, независимо от создания и статуса. Уже подтверждённые отображаются, но не требуют повторного подтверждения. Проверять конкретный документ можно в любой день, не дожидаясь плановой проверки.

На экране проверки показывать границы, дату проверки, категории, карточки и итоги по статусам. Документы без вложения и документы с отклонёнными отметками остаются видимыми как незавершённые. На самой проверочной пятнице срок «сегодня» ещё не является просрочкой.

Отдельно показывать незавершённые документы прошлых периодов, в том числе со сроком до 14.11.2026. Не терять старые ожидающие подтверждения карточки, даже если они вложены вовремя. Они доступны для отдельной обработки, без неявного включения в массовое действие текущего периода.

Массовое подтверждение:

- выбор отдельных карточек, всех ожидающих в категории либо всех ожидающих в выбранном периоде;
- выбирать только PLACED; состояния IN_PROGRESS, READY, NEEDS_CORRECTION и CONFIRMED не менять;
- при выборе категории массовое действие распространяется только на подходящие карточки этой категории в текущем периоде;
- «Все категории» — явный режим выбора; скрытые фильтром документы не добавлять неожиданно;
- перед подтверждением показать число и область выбора, дать исключить карточки;
- каждое подтверждение сохранить с автором, временем и идентификатором общей операции.

Отдельное действие «Проверка проведена» сохраняет, кто и когда проверил период, и снимок итогов. Оно не подтверждает документы автоматически. Можно завершить проверку при наличии невыполненных документов — итоги показывают проблемы. Повторная проверка создаёт новую запись. Непроведённую проверку после плановой даты выделять, но не блокировать работу.

Расписание изменяемое: дата начала отсчёта и положительный целочисленный интервал в днях. Показывать предварительный расчёт ближайших дат. Не принуждать новые интервалы к пятницам: пятница — следствие начальных настроек. Старые проведённые проверки и их границы неизменны; подтверждения карточек не сбрасываются из-за изменения расписания.

Правило перехода расписания для первой версии: новые настройки вступают в силу после конца текущего периода. Первый новый период начинается на следующий день после старого; заканчивается в первую дату новой последовательности, которая позже этой границы. Это переходный период, он может отличаться от обычной длины. Последующие периоды следуют новому интервалу. В предварительном просмотре явно показать переходный период. До начала первого периода разрешить заменить начальные настройки целиком. Сохранять версии расписания, автора и время изменений; не допускать дыр и пересечений. Это техническое правило по умолчанию, его следует выделить в README.

## 8. Редактирование, удаление, копирование и история

Все рабочие роли редактируют и удаляют любые карточки. Перед удалением показывать подтверждение. Реализовать логическое удаление: исключить карточку из активных списков и счётчиков, но сохранить данные и историю. В истории показать удаление, автора и время. Не выдавать пользователям операцию физического уничтожения аудита.

История доступна всем участникам, включая отдельный фильтр удалённых карточек. Записывать создание, изменение полей со старыми и новыми значениями, оформление, вложение, подтверждение, отклонение, отмену, удаление. Хранить идентификатор автора и отображаемое имя на момент действия, чтобы переименование или отключение пользователя не делало историю непонятной. Пользователь не может редактировать историю.

«Создать копию» открывает форму новой карточки с названием и категорией исходной. Срок нужно выбрать заново. Новая карточка получает IN_PROGRESS и текущего автора; отметки, даты вложения, подтверждения и история исходной карточки не копируются. Это основной способ создания похожих еженедельных документов.

Категории с документами не удалять каскадно. Предложить перенос карточек или скрытие категории после обработки документов. История сохраняет прежнюю категорию.

## 9. Экраны и интерфейс

1. Главная: название приложения, имя и роль пользователя, плитки категорий, переходы к проверкам и истории. Настройки доступны по правам.
2. Категория: список карточек, создание, поиск по названию, фильтры статуса и срока; по умолчанию ближайшие сроки первыми. Просрочку выделять и цветом, и текстом.
3. Карточка: поля, срок, статус, авторы отметок, разрешённые действия, редактирование, копирование, удаление, история.
4. Форма создания/редактирования: название, срок, категория при переносе; ошибки рядом с полями.
5. Проверки: выбор периода, итоги, категории, индивидуальный и массовый выбор, фиксация проверки, прошлые незавершённые документы.
6. История: действия с фильтром по карточке, участнику, типу события; доступ к удалённым карточкам только для просмотра.
7. Управление: участники и роли, категории, расписание, передача администрирования.
8. Экран отсутствия доступа для неизвестного или отключённого аккаунта; без раскрытия документов.

Сделать спокойный, читаемый интерфейс с крупными кнопками, корректными состояниями загрузки, пустых списков, сетевой ошибки и успешного сохранения. Поддержать светлую/тёмную тему Telegram и длинные названия. Не использовать цвет как единственное обозначение статуса. Не добавлять элементы имитации рабочего стола.

## 10. Совместная работа и целостность

Изменения доступны остальным открытым клиентам без ручного обновления страницы. Цель при нормальном соединении — не позднее 5 секунд после сохранения на сервере. При разрыве соединения показывать состояние и после восстановления получать актуальные данные. Не показывать несохранённое действие как успешно завершённое.

Защитить от одновременного редактирования и устаревшего подтверждения: у карточки версия, операции передают ожидаемую версию. При конфликте не перезаписывать чужие изменения; показать уведомление и свежие данные. Массовая операция повторно проверяет роли, статусы и версии на сервере. Допустим частичный успех с точным итогом «подтверждено / пропущено / конфликт», без ложного общего успеха. Повтор запроса после сбоя не создаёт дубли событий.

## 11. Технический ориентир для реализации

Это предлагаемый вариант, а не утверждение о единственно правильном стеке. Для нового проекта можно использовать TypeScript, React, сервер Node.js и PostgreSQL с миграциями. Выбор библиотек и актуальных версий сделать при реализации по официальной документации; закрепить зависимости. Для обновлений использовать SSE/WebSocket либо опрос с интервалом до 5 секунд и корректным восстановлением.

- Источник истины — сервер и БД; localStorage не заменяет БД.
- На сервере проверять подлинность Telegram initData и допустимую давность, затем доступ участника. Не доверять initDataUnsafe, переданным клиентом ролям и user ID без проверки. Точную процедуру интеграции сверить с актуальной официальной документацией Telegram.
- Права проверять на каждом серверном действии, в том числе массовом. Отзыв доступа и смена роли должны действовать на уже открытые сессии.
- Bot token, ключи и строки подключения — только серверные переменные окружения. Не включать в клиентский bundle, репозиторий и журналы запросов.
- Часовой пояс приложения по умолчанию Europe/Moscow. Даты срока и фактического вложения хранить как date; времена событий — в UTC с отображением в часовом поясе приложения.
- Изменение карточки и запись события аудита — одна транзакция. Подтверждение привязано к версии значимых данных.
- Предусмотреть сущности User, Category, Document, AuditEvent, ScheduleVersion, ReviewPeriod, ReviewRecord и BatchOperation либо эквивалентную модель.
- Для ReviewRecord сохранять снимок проверенных карточек, их версий и итогов: последующие изменения и удаления не переписывают результат прошлой проверки. Текущий список периода может отличаться от исторического снимка, это обозначать.
- Начальную привязку администратора выполнить по конфигурации один раз; последующие передачи хранить в БД, не отменять их при перезапуске.
- Ограничение на длину названия по умолчанию — 200 символов. Причину отклонения/отмены также ограничить разумной длиной. Данные валидировать на сервере.
- Предусмотреть инструкции резервного копирования и восстановления БД. Данные переживают перезапуск.
- В режиме разработки разрешён явный тестовый вход за роли с синтетическими данными. Он должен быть отключён и недоступен в production; клиентский переключатель ролей не заменяет авторизацию.

## 12. Критерии приёмки

1. Неизвестный Telegram-пользователь не читает и не изменяет данные. Подмена роли в запросе не даёт права подтверждения.
2. Четыре работника видят одинаковые карточки. Карточку одного работника может оформить и вложить другой, оба автора правильно отражаются.
3. Создание требует название и срок. Карточка появляется в нужной категории у другого клиента без перезагрузки не позднее 5 секунд при нормальной связи.
4. READY не считается вложением и не останавливает просрочку.
5. Прямая отметка вложения из IN_PROGRESS работает; не создаётся фиктивное событие оформления.
6. Можно выбрать прошлую фактическую дату, нельзя будущую. Время нажатия не подменяется выбранной датой.
7. Вложение в последний день и подтверждение неделей позже считается своевременным. Вложение на следующий день — с опозданием на один день. Проверить границу полуночи Europe/Moscow.
8. Работник не может подтвердить, отклонить или массово подтвердить через интерфейс и прямой API. Начальник может подтвердить собственную отметку.
9. Отклонение требует причину; отклонённая дата не закрывает просрочку. Повторное вложение и последующее подтверждение работают, история сохраняется.
10. Для исходного расписания нет проверки 13.11.2026. Есть периоды 14–27.11 и 28.11–11.12. Проверить включение обеих границ и исключение соседних дат.
11. Отбор периода идёт по сроку, а не по созданию/вложению. Подтверждённая заранее карточка не требует повторного подтверждения.
12. Массовое подтверждение затрагивает только выбранные PLACED в явной области. Можно исключить отдельную карточку; документы других категорий и периодов не меняются неявно.
13. Проверку можно отметить проведённой при несданных документах; их статусы не меняются. Старые незавершённые документы остаются доступны.
14. Изменение расписания показывает переходный период, не создаёт пропусков/пересечений и не меняет исторические проверки и подтверждения.
15. Изменение значимых полей подтверждённой карточки снимает подтверждение с историей. Неизменённые данные не снимают его.
16. Удаление любым работником убирает карточку из активного списка, но оставляет её историю и прежний снимок проверки.
17. Копия получает новый ID, новый срок и IN_PROGRESS без отметок оригинала.
18. Два клиента не перетирают правки друг друга. Изменённая после выбора карточка не подтверждается по устаревшей версии. Повтор запроса не дублирует событие.
19. Передача администратора переживает перезапуск. Отключённый пользователь теряет доступ, его старые действия остаются читаемыми.
20. После перезапуска сервера/БД данные сохранены. Сетевая ошибка не выдаётся за успешное сохранение.
21. Проверены мобильная и широкая ширина, длинные названия, пустые состояния, светлая и тёмная темы. Уведомлений от бота и загрузки документов нет.

Автоматизировать тесты прав, переходов, сроков, периодов, конфликтов и сохранения истории. Дополнить интеграционными тестами и проверкой двух одновременных клиентов. Реальный запуск внутри Telegram проверить после получения реквизитов; не объявлять его проверенным по одному браузерному макету.
